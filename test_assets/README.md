# LMIS Pipeline Regression Fixtures — Synthetic Lab Report

One synthetic laboratory report, taken through every stage of the LMIS
pipeline, with the expected output at each stage captured as a
fixture file. Patient, physician, and lab identifiers are entirely
fictional (name, MRN, Aadhaar/PAN, phone, email, address are all
invented and don't correspond to a real person).

```
Upload → Ingestion → OCR → PHI Tokenization → NER → Normalization →
Trend → Knowledge → Reasoning → Verification
```

| File | Stage | How it was produced |
|---|---|---|
| `01_synthetic_lab_report.txt` | source document | hand-authored |
| `02_expected_ocr_output.json` | OCR | hand-built `RawExtraction` (simulates OCR span output) |
| `03_expected_phi_tokenized.json` | PHI Tokenization | **real code**: `PHITokenizer` from the PHI tokenization module |
| `04_expected_ner_entities.json` | NER | **real code**: `NERAgent` against the project's actual `knowledge_base/ontologies/*.json` |
| `05_expected_normalized_entities.json` | Normalization | **real code**: `NormalizationAgent` against the project's actual `knowledge_base/reference_ranges/lab_reference_ranges.json` |
| `06_expected_trend_output.json` | Trend | derived from documented code behavior (see notes below), not a live run |
| `07_expected_knowledge_topics.json` | Knowledge | **mock** — queries are derived from real code, retrieval results are hand-authored (needs a live Qdrant store) |
| `08_expected_reasoning_insights.json` | Reasoning | **mock** — evidence pool is derived from real code, LLM response is hand-authored |
| `09_expected_verification_results.json` | Verification | **mock** — builds on the reasoning mock; LLM response is hand-authored |

`document_id = 11111111-1111-4111-8111-111111111111`,
`patient_id = 22222222-2222-4222-8222-222222222222` — fixed throughout so every stage's UUIDs (e.g. the `entity_id`s referenced in Reasoning) are cross-checkable and recomputable.

## Why stages 1–5 are exact-match regression targets and 6–9 aren't

Stages 1–5 (OCR → PHI Tokenization → NER → Normalization) are pure,
deterministic, rule-based code in this project today — no LLM, no
external service. Fixtures 02–05 were generated by literally running
that code (`PHITokenizer`, `NERAgent`, `NormalizationAgent`) against
`01_synthetic_lab_report.txt`'s content, so they're safe to assert on
with `==` in a test suite, with two caveats documented inline in the
files themselves:

- `NERAgent.temp_id` is `uuid4().hex` — **randomly generated per run**,
  by design (see `agents/ner/agent.py`). Fixtures 04/05 replace it with
  stable placeholders `TEMP-01`..`TEMP-11` (ordered by
  `source_span_start`, which *is* deterministic). A real test should
  either monkeypatch `uuid4` to a fixed sequence, or compare entities
  by `(entity_label, source_span_start)` instead of `temp_id`.
- Wall-clock fields (`processing_time_ms`) are obviously non-deterministic
  and should be excluded from equality checks (assert type/range instead).

Stage 6 (Trend) is deterministic code but depends on `entity_date`,
which `NERAgent` never populates today (a documented, in-progress
limitation — see `agents/ner/agent.py`'s module docstring). Given that,
the *correct* expected output for a single report is genuinely
`trends: [], gaps: [], insufficient_data_metrics: []` — this fixture
is real and assertable today, it's just not the fixture you'd get once
`entity_date` support ships.

Stages 7–9 (Knowledge, Reasoning, Verification) call a live vector
store and an LLM respectively. Those aren't deterministic across
providers/versions even at temperature 0, so there's no way to
hand-derive a byte-exact "expected" output the way stages 1–5 were
derived. Each of those three files instead gives you:
1. The **deterministic part** your own code computes today (retrieval
   queries in 07, the evidence pool in 08, the draft-insight input in 09)
   — safe to assert on exactly.
2. A **mock upstream response** (vector-store hits / LLM completion)
   plausible enough to stub `vector_store.search()` / `llm_provider.llm()`
   with in a test.
3. The **deterministic post-processing output** your own code would
   produce from that mocked input — also safe to assert on exactly,
   once the mock is wired in.

## Notable, intentional findings baked into this fixture

- **RBC, MCV, MCH, MCHC are in the report text but never extracted.**
  `knowledge_base/ontologies/loinc_codes.json` has no aliases for them;
  NER is dictionary-driven, not a statistical model, so out-of-dictionary
  analytes are silently skipped. Real, current behavior — not a bug in
  this fixture.
- **Hematocrit, Platelets, and Triglycerides code successfully but get
  `reference_range_* = null`.** `lab_reference_ranges.json` has no entries
  for LOINC `4544-3`, `777-3`, `2571-8` yet.
- **HbA1c's `reference_range` is always `4.0–5.6%`,** eGFR's is always
  `90–999`, and Cholesterol/LDL/HDL always pick the "Desirable"/"Optimal"/
  "Normal" band — regardless of the patient's actual value — because
  `ReferenceRangeIndex.get()` always returns the band whose interpretation
  reads as normal when a metric has multiple clinical bands (see
  `agents/normalization/reference_ranges.py`).
- **Hemoglobin's and Creatinine's ranges are sex-agnostic unions**
  (`12.0–17.5`, `0.6–1.3`) because `node_normalization` doesn't currently
  pass `patient_sex`/`patient_age` through — a documented orchestrator
  wiring gap, not something this fixture worked around.
- **A pre-existing bug, unrelated to PHI tokenization**, surfaced while
  building the Knowledge fixture: `agents/knowledge/agent.py` imports
  `KnowledgeItem` from `app.schemas.agent_messages`, but that class isn't
  defined there. Importing the Knowledge agent today raises `ImportError`.
  Flagged in `07_expected_knowledge_topics.json`'s notes; out of scope to
  fix here since this fixture request was for test assets only.

## Regenerating stages 1–5 yourself

The synthetic report's OCR spans, the PHI tokenizer, the NER ontology
matcher, and the normalization reference-range logic are all real,
unmodified project code — feel free to re-run
`PHITokenizer().tokenize(...)`, `NERAgent().extract_entities(...)`, and
`NormalizationAgent().normalize(...)` directly against
`02_expected_ocr_output.json`'s `full_text` to confirm 03/04/05
reproduce exactly (modulo `temp_id`, per above).
